# ADR-0002：V1采用单JAR、本地工具包和本地子进程

- 状态：Accepted
- 日期：2026-08-12
- 取代：旧文档中的隔离Runner、容器镜像和多JDK执行假设

## 背景

项目是维护者个人使用的Java 17 Maven代码审计工具。目标是上传ZIP或SVN地址后执行多个扫描器并下载统一报告。维护者希望部署简单：运行一个Java程序，不安装数据库，不要求Docker，也不维护远程执行服务。

扫描器并不都是Java库。Semgrep、Gitleaks、Trivy、OSV-Scanner和CodeQL包含平台原生程序；SpotBugs、PMD等以Java发行包运行；Dependency/Enforcer/CycloneDX以Maven插件运行。因此无法把所有内容真正封装成一个物理JAR，但可以提供一个启动入口和同目录工具包。

## 决策

- Spring Boot模块化单体打成一个可执行JAR；
- JDK17和Maven3.9+由运行机器安装；
- 扫描器通过Java `ProcessBuilder`在本机按任务启动；
- 参数使用数组，不经Shell；
- 任务、原始报告、统一报告和恢复状态使用文件目录；
- 单实例通过文件锁保护；
- 不引入数据库、Redis、MQ、容器、Kubernetes或独立Runner；
- 执行接口保留`ExecutionBackend`抽象，但V1只有本地实现；
- 只扫描维护者信任的源码；V1不声称隔离恶意Maven项目。

## 影响

### 收益

- 一个启动命令，部署和本机调试简单；
- 没有容器镜像和调度服务开销；
- 扫描器原生命令和报告易于复现；
- 文件状态可以直接检查、备份和清理；
- 适合Mac开发和单台Linux服务器。

### 代价

- Maven插件可以以服务账户权限执行代码；
- 资源限制主要依赖应用调度、工具参数和OS/cgroup，而非容器硬隔离；
- V1只能单实例；
- 原生工具必须按平台分别准备；
- 扫描器升级和Git LFS会增加仓库体积；
- 多用户、恶意上传或水平扩展时必须重新设计。

## 未采用方案

- **每任务Docker容器**：隔离更强，但不符合当前无容器部署目标，并增加镜像、缓存和运维复杂度。
- **独立Runner服务**：便于水平扩展，但需要网络协议、队列、鉴权和状态服务，超出个人V1。
- **全部嵌入JAR**：原生工具和CodeQL许可/体积使其不可行。
- **只调用IDE插件**：需要IDE，不适合Web/API和无人值守扫描。

## 重新评估条件

任意公网上传、多用户/多租户、生产凭据可见、需要多节点扩展或法规要求硬隔离时，本ADR不再适用。
